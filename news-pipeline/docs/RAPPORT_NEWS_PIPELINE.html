1. Contexte et objectifs

Les médias publient chaque jour un volume important d’articles. Ce projet met en place une architecture distribuée pour : collecter automatiquement des articles depuis plusieurs sites ; les ingérer en batch et en streaming ; les stocker dans un data lake (MinIO) selon une architecture médaillon (bronze / silver / gold) ; les transformer (ETL) ; alimenter un entrepôt PostgreSQL ; contrôler la qualité des données ; documenter la gouvernance ; et visualiser les tendances (Grafana).

2. Architecture technique

  • Scraping : Python, BeautifulSoup, requests — sources configurées (Maroc + international).
  • Ingestion : événements JSON vers Kafka (topic raw-articles) + fichiers JSON dans MinIO bronze.
  • Streaming : consumer Kafka → nettoyage léger → MinIO silver.
  • Batch : DAG Apache Airflow (news_pipeline) planifié à l’heure : scraping one-shot → bronze→silver → silver→gold (DW + résumé JSON dans MinIO gold).
  • Data Warehouse : PostgreSQL (news_dw) — tables de faits et d’agrégats (par jour, source, thème, pays, mots-clés, contrôles DQ).
  • Visualisation : Grafana connecté au DW.

4. Schéma du pipeline Airflow

scrape_articles → bronze_to_silver → silver_to_gold → data_quality_check

Le scraper lancé par Airflow utilise la variable d’environnement SCRAPER_ONCE=1 pour une exécution unique (sans boucle infinie).

5. Qualité et gouvernance

  • Qualité : contrôles sur titres vides, dates, contenu court, URLs invalides, doublons — enregistrement dans dq_checks avec dimension (complétude, validité, cohérence).
  • Gouvernance : inventaire data_catalog décrivant les jeux de données et couches (bronze, silver, gold, ingestion).

6. Déploiement

cd news-pipeline
docker compose build airflow scraper
docker compose up -d

Premier démarrage : le build airflow installe les dépendances Python dans l’image (plus fiable que l’installation à chaud au démarrage).

7. Pourquoi l’interface Airflow peut « ne pas fonctionner » — causes et solutions

7.1 Le navigateur affiche « impossible d’accéder au site »

  • Cause : conteneur pas encore prêt ou arrêté.
  • Solution : docker compose ps — airflow-webserver doit être Up. Sinon docker compose logs airflow-webserver --tail 150 et docker compose logs airflow-init.

7.2 Délai long avant que le port 8080 réponde

  • Cause : migration airflow db migrate, création utilisateur, démarrage webserver + scheduler.
  • Solution : attendre 2–5 minutes après up -d ; surveiller les logs jusqu’à voir le webserver écouter.

7.3 Port 8080 déjà utilisé (conflit)

  • Cause : autre application sur 8080.
  • Solution : libérer le port ou modifier dans docker-compose.yml la publication, ex. "8081:8080" puis ouvrir http://localhost:8081

7.4 PostgreSQL pas prêt au moment de la migration Airflow

  • Cause : course au démarrage.
  • Solution : le compose utilise un healthcheck Postgres ; si problème persiste, docker compose restart airflow.

7.5 Docker Desktop — mémoire insuffisante

  • Cause : Airflow + Kafka + autres services consomment de la RAM.
  • Solution : Docker Desktop → Settings → Resources → augmenter la RAM (ex. ≥ 6 Go si possible).

7.6 URL incorrecte

  • Solution : utiliser http://127.0.0.1:8080 au lieu de localhost si résolution DNS locale pose problème.
Identifiants par défaut (démo) : utilisateur admin, mot de passe admin — à changer en environnement réel.

8. Limites et évolutions

  • Les sélecteurs HTML des sites évoluent : le scraping peut nécessiter des mises à jour.
  • La détection de « fake news » est mentionnée comme piste (catalogue) ; un modèle ML serait une extension.
  • Séparer la base métadonnées Airflow de la base news_dw serait recommandé en production.

9. Conclusion

La solution respecte les exigences du sujet : collecte multi-sources, ingestion batch et streaming, lac MinIO, médaillon, ETL orchestré par Airflow, entrepôt analytique, contrôles de qualité, inventaire de gouvernance et visualisation Grafana.
